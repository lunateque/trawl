# trawl — дизайн

Дата: 2026-11-23. Статус: на ревью у владельца.

## Зачем

`trawl` скачивает музыку в локальную библиотеку. Решает три вещи:
- **что скачать** — по вкусу владельца;
- **откуда** — из лучшего доступного источника;
- **как назвать и протегировать** — так, чтобы любой плеер собрал альбомы правильно.

Это замена `D:/musicpipe/pipeline.py` и его спутников, написанная с нуля. Старая библиотека, `state.sqlite` и Muse не затрагиваются и не читаются. С плеерами trawl связан только через папку с файлами и тегами.

## Цели

1. **Качество звука.** Файл сохраняется таким, каким пришёл из источника, без пережатия. Без потерь в приоритете.
2. **Точность.** Каждый скачанный файл подтверждён: это та запись, которая была запланирована. Меньше «не нашлось», ноль тихо неверных треков.
3. **Полные теги.** MusicBrainz ID, несколько исполнителей, диски, даты, ISRC, жанр, обложка, синхронные тексты, ReplayGain.
4. **Автоматика.** Сам подхватывает новые лайки и новые релизы отслеживаемых артистов.
5. **План по вкусу.** Источники вкуса: ListenBrainz, Яндекс Музыка, Spotify, ручное добавление. Жанры и пороги задаются в конфиге, не в коде.
6. **Переносимость.** Конфиг вместо зашитых путей, одинаковая работа на Windows и Linux.
7. **Терминальный интерфейс.** CLI для всего плюс TUI для наблюдения и ручных решений. Веба нет.

## Не цели

- Скачивание из Deezer, Qobuz, Tidal и других стримингов в обход их защиты.
- Воспроизведение, сервер, синхронизация на телефон, публикация на VPS.
- Миграция или правка старой библиотеки `D:/musicpipe/lib`.
- Распознавание произвольных неизвестных файлов «как beets». Каждый файл в trawl скачивается под заранее известную запись. Исключение — папка своих файлов (см. «Источники»), но и там файл сопоставляется с релизом MusicBrainz.

## Обзор

```
вкус ──► желания ──► план (релиз MusicBrainz, треки с MBID)
                         │
                         ▼
          источники по приоритету: свои файлы → Soulseek → YouTube Music
                         │  кандидат
                         ▼
          скачивание ──► проверка (AcoustID / длительность) ──► теги ──► библиотека
                         │ отказ
                         └──► следующий кандидат / следующий источник
```

Главный принцип: **сначала план, потом звук.** Ещё до поиска каждый трек привязан к конкретному релизу и записи MusicBrainz. Источники поставляют только звук. Теги никогда не угадываются по имени файла или заголовку видео.

## Технологии

- Python 3.12+, пакет в `src/trawl`, установка и запуск через `uv`.
- `httpx` (async) для HTTP, `mutagen` для тегов, `yt-dlp` как библиотека, `ytmusicapi`, `pyacoustid`, `typer` для CLI, `textual` для TUI, `platformdirs` для путей по умолчанию, stdlib `sqlite3` и `tomllib`.
- Внешние программы: `ffmpeg` (ремукс без перекодирования), `fpcalc` (Chromaprint), `rsgain` (ReplayGain). Сервис `slskd` нужен только для источника Soulseek. Команда `trawl doctor` проверяет наличие и версии всего этого.
- Проверки: `ruff` (lint и format), `pyright` в strict, `pytest`. CI в GitHub Actions на Windows и Ubuntu.

## Раскладка пакета

```
src/trawl/
  cli.py            команды typer
  config.py         загрузка и проверка TOML, секреты
  db/               схема, миграции (нумерованные .sql), запросы
  net/              общий httpx-клиент, лимитеры на сервис, повторы
  mb/               клиент MusicBrainz и Cover Art Archive
  taste/            listenbrainz.py, yandex.py, spotify.py, manual.py, releases.py
  plan/             желание → релиз → треки; правила выбора релиза
  sources/          base.py (протокол), local.py, soulseek.py, ytmusic.py
  verify/           fingerprint.py, policy.py
  tag/              mapping.py (MB → поля), writer.py (FLAC/Opus/M4A/MP3), cover.py, lyrics.py, replaygain.py
  library/          layout.py (пути), place.py (атомарная укладка)
  runner/           очередь, воркеры, состояние трека
  tui/              приложение Textual
```

Каждый модуль отвечает за одно и тестируется отдельно. Сеть изолирована в `net/` и клиентах, поэтому логику выбора релиза, проверки, маппинга тегов и путей можно тестировать как чистые функции.

## Данные

SQLite-файл в каталоге данных trawl (по умолчанию `platformdirs.user_data_dir("trawl")`, путь задаётся в конфиге). Режим WAL. Миграции — нумерованные `.sql` с версией в `PRAGMA user_version`.

| Таблица | Назначение | Ключевые поля |
|---|---|---|
| `wants` | что хотим и почему | `kind` (artist, release_group, release, recording, url), `mbid`, `query`, `scope` (track, album, discography), `origin` (listenbrainz, yandex, spotify, manual, releases), `origin_ref`, `status`, `created_at` |
| `artists` | известные артисты | `mbid`, `name`, `sort_name`, `followed`, `tier` |
| `releases` | выбранные релизы | `mbid`, `release_group_mbid`, `title`, `artist_credit`, `date`, `original_date`, `type`, `track_count`, `disc_count`, `choice_reason` |
| `tracks` | треки к скачиванию | `release_mbid`, `release_track_mbid`, `recording_mbid`, `disc`, `position`, `title`, `artist_credit`, `length_ms`, `isrc`, `want_id`, `state`, `source`, `codec`, `lossless`, `bitrate`, `verified_by` (acoustid, duration, manual), `path` |
| `attempts` | каждая попытка | `track_id`, `source`, `candidate_ref`, `outcome`, `reason`, `score`, `at` |
| `kv` | курсоры синхронизации вкуса, время последних проверок | `key`, `value` |

Состояния трека: `planned → searching → fetched → verified → tagged → done`; финальные `missing` (ни один источник не дал подтверждённого файла) и `skipped` (решение владельца). Переходы делает только `runner`, каждый переход — одна транзакция. Прерванная работа продолжается с последнего зафиксированного состояния. Скачанные, но ещё не проверенные файлы лежат во временной папке внутри каталога данных и чистятся при старте.

## Вкус → желания

У каждого желания хранится происхождение (`origin`, `origin_ref`), чтобы `trawl explain` мог ответить, почему трек оказался в библиотеке.

- **ListenBrainz** (`sync-taste listenbrainz`, имя пользователя в конфиге). Берутся топ артистов и записей за период. Артисты распределяются по уровням по числу прослушиваний: пороги и `scope` каждого уровня задаются в конфиге. По умолчанию повторяются старые: уровень 1 — дискография до 14 альбомов, уровень 2 — до 10, уровень 3 — до 3, уровень 4 — 1 альбом.
- **Яндекс Музыка** (`sync-taste yandex`, токен в секретах, неофициальный клиент `yandex-music`). Лайки и выбранные плейлисты. Трек сопоставляется с записью MusicBrainz по ISRC, если он есть, иначе поиском по артисту, названию и длительности. Несопоставленные треки становятся желаниями `kind=url` и видны в `status`.
- **Spotify** (`sync-taste spotify`, OAuth PKCE со своим client id из секретов). Лайки и выбранные плейлисты. Сопоставление по ISRC, который Spotify отдаёт почти всегда.
- **Вручную**: `trawl add <артист|альбом|ссылка MusicBrainz|ссылка YouTube Music|ссылка Spotify|ссылка Яндекса>`, флаг `--scope`.
- **Новые релизы** (`sync-taste releases`): для артистов с `followed=1` из MusicBrainz берутся группы релизов, вышедшие после последней проверки. Типы, которые считаются новым релизом, задаются в конфиге (по умолчанию album и EP).

Желание-трек (лайк) по умолчанию раскрывается в один трек его исходного альбома, а не в весь альбом. Правило настраивается: `likes.scope = "track" | "album"`.

## План

Желание превращается в релиз MusicBrainz и список треков. Правила выбора релиза внутри группы:
- статус Official;
- тип по фильтру из конфига;
- предпочтение стран по списку из конфига;
- оригинальное издание или расширенное (`prefer = "original" | "deluxe"`);
- цифровой носитель в приоритете, потому что совпадает с тем, что лежит в источниках.

Причина выбора записывается в `releases.choice_reason`.

Одна запись, попавшая в несколько желаний, скачивается один раз: трек уникален по `release_track_mbid`. Запросы к MusicBrainz идут через общий лимитер (1 запрос/с, свой User-Agent с контактом владельца) и кешируются в базе на срок из конфига.

## Источники

Общий протокол:

```python
class Source(Protocol):
    name: str
    async def search(self, release: Release, tracks: list[Track]) -> list[Candidate]: ...
    async def fetch(self, candidate: Candidate, into: Path) -> list[Fetched]: ...
```

Кандидат описывает либо папку целого альбома, либо отдельный трек. В нём указаны ожидаемый формат, битрейт и оценка. Порядок источников и их включение задаются в конфиге. По умолчанию порядок такой:

1. **`local` — свои файлы.** Папки из конфига `sources.local.inbox`: купленное на Bandcamp, рипы. Каждая подпапка — кандидат-альбом. Файлы снимаются отпечатком и сопоставляются с треками релиза. Оригиналы во входящей папке не трогаются: файлы копируются, перемещение включается опцией.
2. **`soulseek` — через REST API slskd.** Поиск по «артист альбом» с запасными формулировками. Ответы группируются по папкам пользователя. Папка проходит, если число аудиофайлов покрывает треки релиза и длительности, когда slskd их отдаёт, совпадают в пределах допуска. Порядок: без потерь выше, затем битрейт, свободный слот, скорость отдачи. Скачивается вся папка, затем каждый файл сопоставляется с треком отпечатком. Для желания-трека ищется и одиночный файл.
3. **`ytmusic` — YouTube Music.** Альбом ищется через `ytmusicapi`, затем сверяется число треков и длительности, затем берутся `videoId` треков альбома с официального канала. Для одиночного трека используется поиск с фильтром `songs`. Скачивание идёт через `yt-dlp` как библиотеку, формат `bestaudio`, затем ремукс в контейнер без перекодирования: Opus → `.opus`, AAC → `.m4a`. Cookies — путь из секретов. «Стена» определяется по типу исключения yt-dlp, после неё источник ставится на паузу с растущим интервалом.

**Апгрейд внутри новой библиотеки.** В режиме `--watch` треки с `lossless=0` периодически перепроверяются в источниках без потерь. Найденная проверенная версия без потерь заменяет файл атомарно. Состояние и путь обновляются, старый файл удаляется.

## Проверка

`verify/policy.py` решает по каждому скачанному файлу:

1. `fpcalc` строит отпечаток, AcoustID ищет по нему записи.
2. Среди результатов есть запланированная `recording_mbid` с уверенностью не ниже порога (по умолчанию 0.80) → **принять**, `verified_by=acoustid`.
3. AcoustID уверенно указывает на другие записи, а нашей среди них нет → **отказ**, причина записывается, пробуется следующий кандидат.
4. AcoustID записи не знает → принять, только если длительность совпадает в пределах ±3 с **и** кандидат высокой надёжности: папка целого альбома, совпавшая по числу треков и длительностям, или трек официального альбома YouTube Music. Тогда `verified_by=duration`. Иначе отказ.
5. Файл повреждён или длиннее/короче более чем на 10 % → отказ без запроса к AcoustID.

AcoustID ограничен 3 запросами в секунду через общий лимитер. Ключ приложения лежит в секретах. Ручной выбор кандидата в TUI ставит `verified_by=manual`.

## Теги

`tag/mapping.py` строит из релиза и трека нейтральный набор полей. `tag/writer.py` пишет его в формат файла по соглашениям Picard, чтобы любой плеер читал теги одинаково.

| Поле | FLAC и Opus (Vorbis comments) | MP4 (M4A) | ID3 (MP3, если источник отдал MP3) |
|---|---|---|---|
| название | `TITLE` | `©nam` | `TIT2` |
| исполнители | `ARTIST` (строка кредита), `ARTISTS` (по одному на значение) | `©ART`, `----:ARTISTS` | `TPE1`, `TXXX:ARTISTS` |
| исполнитель альбома | `ALBUMARTIST` | `aART` | `TPE2` |
| альбом | `ALBUM` | `©alb` | `TALB` |
| трек, диск | `TRACKNUMBER`, `TRACKTOTAL`, `DISCNUMBER`, `DISCTOTAL` | `trkn`, `disk` | `TRCK`, `TPOS` |
| даты | `DATE`, `ORIGINALDATE` | `©day`, `----:ORIGINALDATE` | `TDRC`, `TDOR` |
| ID MusicBrainz | `MUSICBRAINZ_TRACKID` (запись), `MUSICBRAINZ_RELEASETRACKID`, `MUSICBRAINZ_ALBUMID`, `MUSICBRAINZ_RELEASEGROUPID`, `MUSICBRAINZ_ARTISTID`, `MUSICBRAINZ_ALBUMARTISTID` | `----:com.apple.iTunes:MusicBrainz …` | `UFID:http://musicbrainz.org`, `TXXX:MusicBrainz …` |
| прочее | `ISRC`, `LABEL`, `RELEASETYPE`, `RELEASESTATUS`, `GENRE`, `COMPILATION` | аналоги | аналоги |

- **Жанр.** Жанры MusicBrainz релиза, затем артиста. Таблица `genres.map` в конфиге сводит их к своему набору, `genres.artist` задаёт ручной жанр артиста. В пути жанр не участвует.
- **Обложка.** Cover Art Archive, лицевая сторона в полном размере сохраняется как `cover.jpg` в папке альбома. Во все файлы встраивается копия, уменьшенная до 1200 px по длинной стороне. Ответ читается целиком, размер сверяется с `Content-Length`.
- **Тексты.** LRCLIB `get` по артисту, названию, альбому и длительности. Синхронный текст сохраняется в `.lrc` рядом с файлом и встраивается (`LYRICS`, `©lyr`, `USLT`). Если есть только обычный текст, встраивается он. Если текста нет, это не ошибка.
- **ReplayGain.** `rsgain` считает усиление трека сразу, а усиление альбома — когда у релиза скачаны все треки. Для Opus используются теги `R128_*`.

## Библиотека

Корень по умолчанию `D:/music`, задаётся в конфиге. Шаблон пути по умолчанию:

```
{albumartist}/{original_year} - {album}{disambiguation}/{disc_prefix}{track:02} - {title}.{ext}
```

`disc_prefix` — это `1-` и так далее, только если в релизе больше одного диска.

- **Безопасные имена.** Запрещённые символы Windows заменяются, зарезервированные имена (`CON` и другие) получают суффикс. Точки и пробелы в конце имени срезаются. Длина ограничивается так, чтобы путь не превысил лимит.
- **Коллизии.** Два релиза с одинаковым путём без учёта регистра различаются по `disambiguation`, а при отсутствии его — по году и короткому MBID.
- **Атомарность.** Файл тегируется во временной папке на том же диске, затем переносится через `os.replace`. Плеер никогда не видит недописанный файл.

## Исполнение

- `asyncio`. Блокирующие `yt-dlp`, `fpcalc` и `rsgain` запускаются в пуле потоков или как подпроцессы.
- Лимитеры на сервис: MusicBrainz 1 запрос/с, AcoustID 3/с, LRCLIB и Cover Art Archive мягкий лимит из конфига. Общее число параллельных скачиваний на источник задаётся в конфиге.
- Повторы с экспоненциальным отступом на сетевые ошибки и 5xx. 4xx, кроме 429, сразу считается отказом.
- Ошибка одного трека никогда не останавливает очередь. Ошибка источника целиком (slskd недоступен, «стена» YouTube) ставит на паузу только этот источник.
- Логи: строки JSON в файл в каталоге данных, человекочитаемый вывод в консоль через `rich`.

## Интерфейс

CLI (`trawl …`):

| Команда | Что делает |
|---|---|
| `doctor` | проверяет внешние программы, ключи, доступность slskd, права на папку библиотеки |
| `add <что>` | ручное желание |
| `sync-taste [listenbrainz\|yandex\|spotify\|releases\|all]` | обновить желания из источников вкуса |
| `follow <артист>` / `unfollow` | отслеживать новые релизы |
| `plan` | превратить новые желания в релизы и треки |
| `run [--once\|--watch]` | обработать очередь; `--watch` — по расписанию из конфига: синк вкуса, новые релизы, очередь, апгрейд |
| `status` | сводка по состояниям, источникам, отказам |
| `explain <трек\|альбом>` | происхождение желания, выбор релиза, все попытки и причины отказов |
| `retry [--missing\|--failed]` | вернуть треки в очередь |
| `tui` | интерфейс Textual |

TUI: очередь и прогресс по источникам, лента событий, список отказов. Для отказа можно:
- посмотреть кандидатов с оценками;
- выбрать одного вручную;
- вставить свою ссылку;
- пометить «нет нигде» (`skipped`).

## Конфиг и секреты

- `config.toml` (по умолчанию `platformdirs.user_config_dir("trawl")`, переопределяется `--config` или `TRAWL_CONFIG`). В нём пути, порядок источников, правила выбора релиза, уровни вкуса, жанры, лимиты, расписание.
- `secrets.toml` рядом, отдельный файл, которого нет в репо. В нём токены Яндекса и Spotify, ключ API slskd, ключ AcoustID, путь к cookies YouTube.
- Пример конфига лежит в репо как `config.example.toml`.

## Тестирование

- **Чистые функции** покрываются табличными тестами: выбор релиза, политика проверки, маппинг тегов, шаблон пути и безопасные имена, оценка кандидатов.
- **Клиенты** (MusicBrainz, AcoustID, slskd, LRCLIB, ytmusicapi) тестируются на записанных ответах в `tests/fixtures`. Живой сети в тестах нет.
- **Теги** проверяются на коротких файлах FLAC, Opus, M4A и MP3, которые тест генерирует через `ffmpeg`: записать, перечитать `mutagen`, сравнить.
- **Сквозной тест** прогоняет фейковый источник, который отдаёт сгенерированный файл, через весь путь до библиотеки во временной папке, с подменённым AcoustID.
- CI: `ruff check`, `ruff format --check`, `pyright`, `pytest` на Windows и Ubuntu.

## Порядок сборки

Каждый шаг заканчивается рабочей программой и зелёным CI.

1. Каркас, конфиг и секреты, база и миграции, клиент MusicBrainz, план, `add` для MusicBrainz-ссылок и поиска, `status`, `explain`, `doctor`.
2. Источник `ytmusic`, проверка, теги, обложки, тексты, ReplayGain, библиотека: первый трек от `add` до файла.
3. Источник `soulseek` и апгрейд до без потерь.
4. Источник `local`.
5. Вкус: ListenBrainz, Яндекс, Spotify, сопоставление по ISRC.
6. Новые релизы, `follow`, `run --watch`, запуск через планировщик Windows и systemd.
7. TUI.

## Риски

- **Неофициальные API Яндекса и YouTube Music ломаются без предупреждения.** Клиенты изолированы в своих модулях. Если источник сломан, падает только он, остальные работают дальше.
- **Небольшие артисты могут отсутствовать в MusicBrainz или AcoustID.** Отсутствие в AcoustID закрывает правило длительности. Отсутствие в MusicBrainz trawl не закрывает: такие желания остаются в `status` как несопоставленные. Добавить релиз в MusicBrainz можно руками, после чего `plan` его подхватит.
- **Soulseek — P2P-обмен.** Там принято раздавать. Раздавать ли папку библиотеки через slskd, решает владелец в настройках slskd, trawl это не делает.
- **YouTube и Soulseek — серая зона.** Поэтому репо приватное.
