# trawl — дизайн

Дата: 2026-11-23. Версия 2: внесены правки по ревью. Статус: на ревью у владельца.

## Зачем

`trawl` скачивает музыку в локальную библиотеку. Решает три вещи:
- **что скачать** — по вкусу владельца;
- **откуда** — из лучшего доступного источника;
- **как назвать и протегировать** — так, чтобы любой плеер правильно собрал альбомы.

Это замена `D:/musicpipe/pipeline.py` и его спутников, написанная с нуля. Старая библиотека, `state.sqlite` и Muse не затрагиваются и не читаются. С плеерами trawl связан только через папку с файлами и тегами.

## Цели

1. **Качество звука.** Файл сохраняется таким, каким пришёл из источника, без пережатия. Без потерь — в приоритете.
2. **Точность.** Каждый скачанный файл подтверждён: это та запись, которая была запланирована. Меньше «не нашлось», ноль тихо неверных треков.
3. **Полные теги.** MusicBrainz ID, несколько исполнителей, диски, даты, ISRC, жанр, обложка, синхронные тексты, ReplayGain.
4. **Автоматика.** Сам подхватывает новые лайки и новые релизы отслеживаемых артистов.
5. **План по вкусу.** Источники вкуса: ListenBrainz, Яндекс Музыка, Spotify, ручное добавление. Жанры и пороги — в конфиге, не в коде.
6. **Переносимость.** Конфиг вместо зашитых путей, одинаковая работа на Windows и Linux.
7. **Терминальный интерфейс.** CLI для всего и TUI для наблюдения и ручных решений. Веба нет.

## Не цели

- Скачивание из Deezer, Qobuz, Tidal и других стримингов в обход их защиты.
- Воспроизведение, сервер, синхронизация на телефон, публикация на VPS.
- Миграция или правка старой библиотеки `D:/musicpipe/lib`.
- Распознавание произвольных неизвестных файлов, как это делает beets. Каждый файл в trawl скачивается под заранее известную запись. Папку своих файлов (см. «Источники») trawl тоже сопоставляет с релизом MusicBrainz.

## Обзор

```
вкус ──► желания ──► план (релиз MusicBrainz, треки с MBID)
                         │
                         ▼
          источники по приоритету: свои файлы → Soulseek → YouTube Music
                         │  кандидат
                         ▼
          скачивание ──► проверка (AcoustID / длительность) ──► теги ──► библиотека
                         │ отказ
                         └──► следующий кандидат / следующий источник
```

Главный принцип: **сначала план, потом звук.** Ещё до поиска каждый трек привязан к конкретному релизу и записи MusicBrainz. Источники поставляют только звук. Теги никогда не угадываются ни по имени файла, ни по заголовку видео.

## Технологии

- Python 3.12+, пакет в `src/trawl`, установка и запуск через `uv`.
- Библиотеки:
  - `httpx` (async): HTTP, в том числе AcoustID напрямую, без `pyacoustid`;
  - `mutagen`: теги;
  - `yt-dlp` как библиотека;
  - `ytmusicapi`;
  - `yandex-music`;
  - `typer`: CLI;
  - `textual`: TUI;
  - `rich`: вывод в консоль;
  - `platformdirs`: пути по умолчанию;
  - из stdlib `sqlite3` и `tomllib`.
- Внешние программы:
  - `ffmpeg` и `ffprobe`: нужны yt-dlp для извлечения звука, а trawl ими проверяет целостность и длительность файла;
  - `fpcalc` (Chromaprint);
  - `rsgain` (ReplayGain);
  - сервис `slskd`, только для Soulseek.

  Команда `trawl doctor` проверяет, что всё это есть, и показывает версии.
- Проверки: `ruff` (lint и format), `pyright` strict, `pytest`. CI в GitHub Actions на Windows и Ubuntu.

## Раскладка пакета

```
src/trawl/
  cli.py            команды typer
  config.py         загрузка и проверка TOML, секреты
  db/               схема, миграции (нумерованные .sql), запросы, переходы состояний
  net/              общий httpx-клиент, лимитеры на сервис, повторы, Retry-After
  mb/               клиент MusicBrainz и Cover Art Archive
  resolve/          ссылки и внешние треки (Spotify, Яндекс, YouTube Music) → MBID
  taste/            listenbrainz.py, yandex.py, spotify.py, releases.py
  plan/             желание → релиз → треки; правила выбора релиза
  sources/          base.py (протокол), local.py, soulseek.py, ytmusic.py, score.py
  verify/           probe.py (ffprobe), fingerprint.py (fpcalc + AcoustID), policy.py
  tag/              mapping.py (MB → поля), writer.py (FLAC/Opus/M4A/MP3), cover.py, lyrics.py, replaygain.py
  library/          layout.py (пути), place.py (staging и атомарная укладка)
  runner/           очередь, воркеры, пауза источников
  tui/              приложение Textual
```

Каждый модуль отвечает за одно и тестируется отдельно. Сеть изолирована в `net/` и клиентах. Поэтому выбор релиза, проверка, маппинг тегов, пути и оценка кандидатов — чистые функции.

## Данные

База — файл SQLite в каталоге данных trawl. По умолчанию это `platformdirs.user_data_dir("trawl")`, путь можно задать в конфиге. Режим WAL, `busy_timeout` 5 с. Миграции хранятся в нумерованных `.sql`, версия схемы — в `PRAGMA user_version`.

| Таблица | Назначение | Поля |
|---|---|---|
| `wants` | что хотим и почему | `id`, `kind` (artist, release_group, release, recording), `mbid`, `scope` (track, album, discography; для artist ещё `limit`), `origin` (listenbrainz, yandex, spotify, manual, releases), `origin_ref` (id трека или плейлиста во внешнем сервисе, ссылка), `status`, `created_at` |
| `unresolved` | внешние треки и ссылки, которые не удалось привязать к MusicBrainz | `id`, `origin`, `origin_ref`, `artist`, `title`, `album`, `length_ms`, `isrc`, `upc`, `reason`, `last_try_at` |
| `artists` | известные артисты | `mbid`, `name`, `sort_name`, `followed`, `releases_checked_at` |
| `releases` | выбранные релизы | `mbid`, `release_group_mbid`, `title`, `artist_credit`, `date`, `original_date`, `type`, `status`, `disc_count`, `choice_reason` (JSON) |
| `tracks` | треки к скачиванию | `id`, `release_mbid`, `release_track_mbid` (UNIQUE), `recording_mbid` (индекс), `disc`, `disc_track_count`, `position`, `title`, `artist_credit`, `artist_mbids` (JSON), `length_ms` (NULL допустим), `isrc`, `state`, `pinned_candidate` (JSON, кандидат от `pick`), `source`, `codec`, `lossless`, `bitrate`, `verified_by` (acoustid, duration, manual, reuse), `path`, `next_try_at` |
| `want_tracks` | какие желания привели к треку | `want_id`, `track_id` |
| `attempts` | каждая попытка | `id`, `track_id`, `source`, `candidate_ref`, `score`, `outcome`, `reason`, `at` |
| `source_state` | пауза источника | `source`, `paused_until`, `backoff_s`, `reason` |
| `cursors` | курсоры синхронизации вкуса | `origin`, `value`, `updated_at` |
| `mb_cache` | кеш ответов MusicBrainz | `url`, `body`, `fetched_at` |

**Одна запись в нескольких релизах.** Библиотека строится из альбомов. Если запись есть и в альбоме, и в сборнике, и нужны оба релиза, это два трека: `release_track_mbid` уникален, `recording_mbid` нет (индекс по нему для поиска). Скачивается запись один раз. Перед поиском runner проверяет, нет ли трека с той же `recording_mbid` в `done`. Если есть, вместо поиска копирует его файл в staging, пишет теги своего релиза и ставит `verified_by=reuse` (строка `planned → verified` в таблице). Если исходный файл пропал с диска, reuse не применяется, трек ищется обычным путём. Лайк на запись не создаёт новый релиз, если уже запланирован релиз, который её содержит: желание просто связывается с этим треком через `want_tracks`.

### Значения статусов

- **`wants.status`:**
  - `new` — ещё не обработано `plan`;
  - `planned` — треки созданы;
  - `empty` — у релиза нет подходящих треков по фильтрам;
  - `dropped` — владелец убрал желание командой `drop`; его треки, которые ещё не `done` и не нужны другим желаниям, переходят в `skipped`.
- **`attempts.outcome`:**
  - `accepted`;
  - `rejected_verify` — проверка отклонила;
  - `rejected_probe` — файл повреждён или не той длительности;
  - `fetch_failed`;
  - `no_candidates`.
- **`tracks.state`** — по таблице ниже.

### Переходы трека

Каждый переход — условный `UPDATE … WHERE id=? AND state=?` в одной транзакции. Поэтому runner, TUI и CLI могут работать одновременно и не затирают решения друг друга: если состояние уже сменилось, переход просто не применяется.

| Из | В | Кто | Условие |
|---|---|---|---|
| — | `planned` | `plan` | трек создан из релиза |
| `planned` | `searching` | runner | взят в работу, источник не на паузе |
| `searching` | `fetched` | runner | кандидат скачан в staging |
| `fetched` | `searching` | runner | проверка или пробник отклонили; дальше следующий кандидат |
| `fetched` | `verified` | runner | проверка приняла |
| `verified` | `tagged` | runner | теги записаны в staging |
| `tagged` | `done` | runner | файл перенесён в библиотеку |
| `tagged` | `tagged` с `next_try_at` | runner | перенос не удался (файл занят плеером), повтор с отступом |
| `searching` | `missing` | runner | все источники исчерпаны |
| `searching` | `planned` с `next_try_at` | runner | все подходящие источники на паузе |
| `missing` | `planned` | `retry`, `run --watch` раз в `retry_missing_days` | новая попытка |
| любое, кроме `done` | `skipped` | TUI, `skip` | решение владельца |
| `skipped` | `planned` | `retry --skipped` | владелец передумал |
| `missing`, `searching`, `planned` | `searching` с закреплённым кандидатом | TUI, `pick` | владелец выбрал кандидата из списка или дал свою ссылку; runner скачивает именно его. Отказ AcoustID не отклоняет молча, а показывается владельцу, который может принять файл (`verified_by=manual`) |
| `planned` | `verified` | runner, reuse | есть трек в `done` с той же записью и его файл на месте |
| `done` | `done` | runner, апгрейд | без потерь: новая версия проверяется в staging, затем атомарно заменяет старый файл; трек не покидает `done` |
| `planned`, `missing`, `skipped` | удалён | `plan`, смена издания | трек не входит в новое издание альбома (см. «План») |

Скачанное лежит в staging внутри корня библиотеки (см. «Библиотека»). При старте runner удаляет из staging всё, на что не ссылается ни один трек в `fetched`, `verified` или `tagged`. Это безопасно, потому что runner на базу один (см. «Исполнение»), и чужих файлов в staging быть не может.

## Вкус → желания и ссылки

У каждого желания хранится происхождение. Поэтому `trawl explain` может ответить, почему трек оказался в библиотеке.

**Привязка к MusicBrainz** (`resolve/`). Внешний трек или ссылка проверяется по порядку:

1. ISRC → поиск записей MusicBrainz по `isrc:`. Если записей несколько, берётся та, у которой длительность ближе к исходной, в пределах допуска.
2. Для альбома UPC → поиск релиза по `barcode:`.
3. Поиск по артисту, названию и, если есть, альбому. Принимается, только если score MusicBrainz ≥ 90, артист совпадает после нормализации и длительность попадает в допуск `max(3 с, 2 %)`.
4. Ничего не подошло → строка в `unresolved` с причиной. Её видно в `status` и TUI, а `trawl link <unresolved> <ссылка MusicBrainz>` привязывает вручную.

Нормализация названий для сравнения одна на весь проект: NFKC, casefold, без пунктуации и без суффиксов вида `- Remastered 2011`. Для кириллицы и CJK транслитерации нет: такие названия сравниваются как есть.

**Откуда берутся желания:**
- **ListenBrainz** (`sync-taste listenbrainz`, имя пользователя в конфиге). Записи и артисты из статистики за период из конфига. Уровень артиста вычисляется при каждой синхронизации и не хранится. Пороги прослушиваний и объём на уровень задаются в конфиге; по умолчанию как в старом пайплайне: ≥6 прослушиваний — дискография до 14 альбомов, ≥3 — до 10, 2 — до 3, 1 — 1 альбом. Альбомы дискографии выбираются по числу прослушиваний его записей у владельца, при равенстве — новые раньше.
- **Яндекс Музыка** (`sync-taste yandex`, токен в секретах). Лайки и плейлисты из конфига. ISRC неофициальный API отдаёт не всегда, поэтому часто работает шаг 3.
- **Spotify** (`sync-taste spotify`). OAuth PKCE со своим приложением в Development Mode. Для этого нужен Premium у владельца. На каждый трек уходит отдельный запрос, потому что пакетные эндпоинты убраны. ISRC берётся из `external_ids`.
- **Вручную:** `trawl add <ссылка MusicBrainz | «Артист» | «Артист - Альбом» | ссылка Spotify, Яндекса или YouTube Music>` с флагом `--scope`. Текстовый запрос показывает найденные варианты и требует выбора, если первый вариант не проходит порог шага 3.
- **Новые релизы** (`sync-taste releases`). Для артистов с `followed=1` из MusicBrainz берутся группы релизов с датой позже `releases_checked_at`. Какие типы считаются новым релизом, задаётся в конфиге; по умолчанию album и EP.

**Лайк** (запись из Яндекса или Spotify) по умолчанию — это один трек. Правило `likes.scope`:
- `"track"` — желание `kind=recording, scope=track`;
- `"album"` — желание `kind=release_group, scope=album` для альбома, который выбран по правилам плана.

## План

Желание превращается в релиз и треки.

**Как выбирается группа релизов для записи.** Среди групп, где есть эта запись, берётся самая ранняя группа типа album, у которой есть официальный релиз. Если такой нет, берётся EP, затем single. Сборники (`secondary-type: Compilation`) идут последними.

**Как выбирается релиз внутри группы.** Кандидаты сравниваются по ключам по порядку:
1. статус Official;
2. носитель: цифровой выше CD, CD выше остальных;
3. страна по списку из конфига, `XW` первой;
4. `prefer = "original"` — меньше треков, `"deluxe"` — больше;
5. более ранняя дата;
6. меньший MBID, чтобы ничья всегда разрешалась одинаково.

`choice_reason` — JSON со значениями этих ключей у выбранного релиза и числом сравнённых.

**Треки релиза.** Создаются по `scope` желания: только нужная запись или все треки. Скрытые и pregap-треки, которые MusicBrainz заводит как трек 0 или data track, пропускаются. У треков без длительности `length_ms = NULL`.

**Смена издания в группе.** Источник может найти папку другого издания той же группы, например deluxe вместо стандартного. Если она проходит сопоставление лучше и **ни один трек альбома ещё не `done`**, `plan` переключает альбом на это издание:
- треки, которых нет в новом издании, удаляются;
- недостающие треки добавляются;
- `choice_reason` фиксирует причину.

Если хотя бы один трек уже в библиотеке, издание не меняется: кандидат оценивается только по трекам текущего издания. Так теги всегда описывают то, что лежит в папке, а файлы в библиотеке никогда не перетегируются под другой релиз.

MusicBrainz: не больше 1 запроса в секунду, User-Agent `trawl/<версия> ( <email из конфига> )`. На 503 — отступ с джиттером. Ответы кешируются в `mb_cache` на срок из конфига, по умолчанию 30 дней; при `plan --refresh` кеш не используется.

## Источники

Общий протокол:

```python
class Source(Protocol):
    name: str
    async def search(self, release: Release, tracks: list[Track]) -> list[Candidate]: ...
    async def fetch(self, candidate: Candidate, into: Path) -> list[Fetched]: ...
```

**Кандидат** — либо папка с альбомом, либо один трек. В нём ожидаемые кодек и битрейт, а также оценка из `sources/score.py`.

**Оценка кандидата** — это сумма, где каждое слагаемое считается чистой функцией и проверяется тестом:
- **покрытие** — доля треков релиза, которым сопоставлен файл, ×100;
- **длительности** — −2 за каждую секунду среднего отклонения сопоставленных файлов;
- **качество** — без потерь +30, lossy ≥256 кбит/с +15, ≥160 +5;
- **надёжность** — официальный альбом YouTube Music +10, свободный слот Soulseek +5.

Кандидаты с покрытием ниже порога отбрасываются. Порог в конфиге, по умолчанию 1.0 для альбомного желания и 0 для трекового. Порядок источников задаётся в конфиге, внутри источника кандидаты пробуются по убыванию оценки.

**Аудиофайлы** — `.flac .opus .ogg .m4a .mp3 .wav .aiff .ape .wv`. Writer тегов есть только для первых пяти. `.wav`, `.aiff`, `.ape` и `.wv` без пережатия не протегировать, поэтому в таком виде в библиотеку их не кладём, а перепаковываем в FLAC без потерь (`lossless_repack = true` по умолчанию). Перепаковка разрешена только для целочисленного PCM до 32 бит (`ffprobe`: `pcm_s16le`, `pcm_s24le` и подобные) и для APE. WAV с плавающей точкой и гибридный WavPack (у которого есть lossy-ядро; `ffprobe` показывает это как lossy-профиль, а отсутствие файла коррекции `.wvc` подтверждает) отклоняются: перепаковка не была бы бит в бит. Остальные файлы в папке-кандидате (`.cue`, `.log`, картинки) не сопоставляются и в библиотеку не попадают.

**Сопоставление файлов папки с треками.** Файлы сопоставляются с треками один к одному. Сначала по отпечатку AcoustID (см. «Проверка»), затем оставшиеся — по порядку и длительности. Подпапки `CD1/`, `Disc 2/` и подобные внутри папки-кандидата считаются частями одного релиза и проходятся вместе. Если в папке одни и те же треки лежат в двух форматах, берётся набор без потерь. Папка с одним файлом на весь альбом и `.cue` отклоняется: резать образ по `.cue` trawl не умеет, а такие папки почти всегда есть и в разрезанном виде.

1. **`local` — свои файлы.** Каждая подпапка папок из `sources.local.inbox` — кандидат-альбом. Купленное на Bandcamp, рипы. Файлы копируются, оригиналы не трогаются; перемещение включается опцией `move = true`.
2. **`soulseek` — через REST API slskd.**
   - **Поиск** по «артист альбом» с запасными формулировками: без суффиксов издания, только альбом.
   - **Группировка.** Ответы группируются по папке пользователя; пути пиров с Windows нормализуются, `\` → `/`. Заблокированные файлы (`lockedFiles`) исключаются.
   - **Порядок** — по оценке. Скачивается вся папка-кандидат: файлы кладутся в очередь slskd, трекинг через API передач.
   - **Застой.** Если передача стоит дольше `stall_timeout` (по умолчанию 10 мин), кандидат отменяется и пробуется следующий.
   - **Куда.** Каталог загрузок slskd указывается в конфиге (`sources.soulseek.download_dir`), потому что в Docker он отличается от пути внутри контейнера. Оттуда trawl переносит файлы в staging.
   - **Трековое желание** ищется ещё и как одиночный файл.
3. **`ytmusic` — YouTube Music.** Альбом ищется через `ytmusicapi.search(filter="albums")`, страница берётся через `get_album`. Принимается, если артист альбома совпадает и число треков и их длительности сходятся с релизом. Одиночный трек ищется через `search(filter="songs")`, берётся по артисту, названию и длительности. Скачивание — `yt-dlp` с извлечением звука в режиме `best`: дорожка сохраняется в своём кодеке, Opus → `.opus`, AAC → `.m4a`, без перекодирования. Cookies лежат по пути из секретов.

   **«Стена» YouTube.** yt-dlp бросает общие `DownloadError`/`ExtractorError`. Поэтому «стена» распознаётся по HTTP-статусу 403/429 в причине или по известным фразам («Sign in to confirm», «not a bot»). Сопоставление собрано в одном месте, `sources/ytmusic.py`, и покрыто тестами. После «стены» источник встаёт на паузу через `source_state`: отступ удваивается от 15 мин до 24 ч и сбрасывается после первого успеха.

**Апгрейд внутри новой библиотеки.** В режиме `--watch` треки в `done` с `lossless=0` перепроверяются в источниках без потерь, по умолчанию раз в 14 дней. Найденная проверенная версия без потерь атомарно заменяет файл, затем пересчитывается ReplayGain альбома.

## Проверка

**Пробник** (`verify/probe.py`) смотрит файл через `ffprobe`, кодек и длительность, и полностью декодирует его через `ffmpeg -v error -f null -`. Отказ (`rejected_probe`), если декодер выдаёт ошибки или длительность вне допуска.

**Допуск длительности** — `max(3 с, 2 %)` от `length_ms`. Если `length_ms = NULL`, длительность не проверяется. Такой трек принимается только по AcoustID или вручную.

**AcoustID** (`verify/fingerprint.py`):
- `fpcalc -json` строит отпечаток по первым 120 с;
- затем `POST https://api.acoustid.org/v2/lookup` с `client`, `duration`, `fingerprint`, `meta=recordingids`;
- лимит — 3 запроса в секунду;
- ключ приложения хранится в секретах.

AcoustID бесплатен только для некоммерческого использования, а trawl — личный инструмент, так что условие выполняется.

**Политика** (`verify/policy.py`). Порог `S` по умолчанию 0.80. «Результаты» — ответы с score ≥ `S`, у которых есть `recordings`.

| Ситуация | Решение |
|---|---|
| в результатах есть запланированная `recording_mbid` | принять, `acoustid` |
| в результатах её нет, но после запроса к MusicBrainz одна из записей результатов оказывается запланированной (MusicBrainz отдаёт новый MBID по старому после слияния) или имеет тот же ISRC | принять, `acoustid` |
| результаты есть, нашей записи среди них нет | отказ `rejected_verify` |
| результатов нет (пустой ответ, score < `S` или нет `recordings`) | правило длительности ниже |
| трек короче 30 с | правило длительности, отпечаток для таких ненадёжен |

**Правило длительности.** Трек принимается с `verified_by=duration`, только если выполнены три условия:
1. длительность в допуске;
2. кандидат надёжный: папка с полным покрытием или официальный альбом YouTube Music, совпавший по числу треков;
3. внутри такой папки ни один другой файл не получил отказ по AcoustID.

Иначе отказ.

**Ремастеры.** Если MusicBrainz завёл ремастер отдельной записью, а AcoustID уверенно показывает оригинал, файл отклоняется. Ремастер — это другой звук, а мы хотим ровно запланированное.

## Теги

`tag/mapping.py` строит из релиза и трека нейтральный набор полей. `tag/writer.py` пишет их по таблице соответствия Picard ([tag mapping](https://picard-docs.musicbrainz.org/en/latest/appendices/tag_mapping.html)). Тест сверяет имена с таблицей, зафиксированной в `tests/fixtures/picard_mapping.json`. Ниже основные поля; где у Picard для формата нет поля, используется freeform-тег с тем же именем.

| Поле | Vorbis (FLAC, Opus, Ogg Vorbis) | MP4 (M4A) | ID3v2.4 (MP3) |
|---|---|---|---|
| название | `TITLE` | `©nam` | `TIT2` |
| исполнители | `ARTIST` (строка кредита), `ARTISTS` (по значению на артиста) | `©ART`, `----:com.apple.iTunes:ARTISTS` | `TPE1`, `TXXX:Artists` |
| исполнитель альбома | `ALBUMARTIST` | `aART` | `TPE2` |
| альбом | `ALBUM` | `©alb` | `TALB` |
| трек, диск | `TRACKNUMBER`, `TRACKTOTAL` (на диске), `DISCNUMBER`, `DISCTOTAL` | `trkn`, `disk` | `TRCK` (n/всего на диске), `TPOS` |
| даты | `DATE`, `ORIGINALDATE` | `©day` | `TDRC`, `TDOR` |
| запись, трек релиза | `MUSICBRAINZ_TRACKID`, `MUSICBRAINZ_RELEASETRACKID` | `----:com.apple.iTunes:MusicBrainz Track Id`, `…Release Track Id` | `UFID:http://musicbrainz.org`, `TXXX:MusicBrainz Release Track Id` |
| релиз, группа | `MUSICBRAINZ_ALBUMID`, `MUSICBRAINZ_RELEASEGROUPID` | `…MusicBrainz Album Id`, `…Release Group Id` | `TXXX:MusicBrainz Album Id`, `TXXX:MusicBrainz Release Group Id` |
| артисты | `MUSICBRAINZ_ARTISTID`, `MUSICBRAINZ_ALBUMARTISTID` (по значению) | `…MusicBrainz Artist Id`, `…Album Artist Id` | `TXXX:MusicBrainz Artist Id`, `TXXX:MusicBrainz Album Artist Id` |
| тип, статус | `RELEASETYPE`, `RELEASESTATUS` | `…MusicBrainz Album Type`, `…Album Status` | `TXXX:MusicBrainz Album Type`, `TXXX:MusicBrainz Album Status` |
| прочее | `ISRC`, `LABEL`, `GENRE`, `COMPILATION` | `----:…ISRC`, `----:…LABEL`, `©gen`, `cpil` | `TSRC`, `TPUB`, `TCON`, `TCMP` |
| обложка | `METADATA_BLOCK_PICTURE` (Opus), блок PICTURE (FLAC) | `covr` | `APIC` |
| текст | `LYRICS` | `©lyr` | `USLT` |

**Жанр.** Берутся жанры MusicBrainz релиза, если их нет — артиста, до 3 с наибольшим числом голосов. В конфиге можно задать два правила: `[genres.map]` (сводит сырые жанры к своим, по умолчанию пусто) и `[genres.artist]` (ручной жанр артиста, побеждает остальное). В пути жанр не участвует.

**Обложка.** Cover Art Archive:
- `/release/<mbid>/front` (полный размер) сохраняется в папку альбома как `cover.jpg`;
- `/release/<mbid>/front-1200` встраивается во все файлы.

У httpx включено `follow_redirects`, потому что CAA отвечает редиректом на archive.org. Ответ читается целиком и сверяется с `Content-Length`. Если у релиза нет лицевой обложки (404), пробуется обложка группы релизов (`/release-group/<mbid>/front`). Если нет и её, альбом остаётся без обложки, это не ошибка.

**Тексты.** Запрос к LRCLIB `GET /api/get` по артисту, названию, альбому и длительности в секундах. User-Agent как у trawl, минимум 300 мс между запросами, на 429/503 соблюдается `Retry-After`. Синхронный текст сохраняется в `.lrc` рядом с файлом: этот формат читают Navidrome, Jellyfin и большинство Subsonic-клиентов. Встраивается обычный текст: синхронный без меток, если обычного нет. Если текста нет вовсе, это не ошибка.

**ReplayGain.** `rsgain custom -s i -o s`: `-s i` пишет теги, `-o s` переводит Opus на `R128_TRACK_GAIN`/`R128_ALBUM_GAIN` относительно −23 LUFS по RFC 7845, без `REPLAYGAIN_*`. Имена флагов зависят от версии rsgain, поэтому `doctor` сверяет их с `rsgain custom --help`, а тест на Opus проверяет, что в файле появился `R128_TRACK_GAIN`.
- **Трек** обрабатывается в staging до переноса в библиотеку, только усиление трека.
- **Альбом.** Когда у релиза все треки `done`, и после каждого апгрейда, `rsgain -a` прогоняется по папке альбома в библиотеке. Файл, который держит плеер, получает повтор с отступом. Это единственный случай, когда trawl переписывает файл, уже лежащий в библиотеке.

## Библиотека

Корень по умолчанию `D:/music`, задаётся в конфиге. Шаблон пути по умолчанию:

```
{albumartist}/{original_year} - {album}{disambiguation}/{disc_prefix}{track:02} - {title}.{ext}
```

`disc_prefix` = `1-` и т. д., только если в релизе больше одного диска. `{disambiguation}` — ` (комментарий MusicBrainz)`, если он есть.

- **Staging** — папка `.trawl-staging/` внутри корня библиотеки, то есть на том же томе. Поэтому перенос — это атомарный `os.replace`. На Windows точка папку не скрывает, поэтому trawl ставит ей атрибут «скрытый». Плееры, которые всё равно её сканируют, исключают её в своих настройках; `doctor` об этом напоминает.
- **Безопасные имена.** Запрещённые на Windows символы заменяются. Зарезервированные имена (`CON` и другие) получают суффикс `_`. Точки и пробелы в конце обрезаются. Каждый компонент — не длиннее 120 символов, весь путь — не длиннее 240.
- **Коллизии.** Если пути двух разных релизов совпадают без учёта регистра, ко второму добавляется ` [<первые 8 символов MBID>]`.
- **Перенос в занятый файл** (Windows, `PermissionError`): повтор с отступом через `next_try_at`, трек остаётся `tagged`.

## Исполнение

- **Блокировка.** На базу работает один runner: `run --once`, `run --watch` и `tui` (в TUI runner встроен) берут блокировку ОС на файл `trawl.lock` в каталоге данных (`msvcrt.locking` на Windows, `fcntl.flock` на Linux). ОС снимает её сама, если процесс упал. Если блокировка занята, `run` выходит с кодом 3 и сообщением, кто её держит (PID из файла), а `tui` открывается в режиме наблюдения. Ручные решения (`skip`, `pick`, `retry`, `drop`, `link`) и в этом режиме пишутся в базу условными переходами, и работающий runner их подхватывает.
- **Параллельность.** `asyncio`; блокирующие `yt-dlp`, `fpcalc`, `ffprobe` и `rsgain` запускаются в пуле потоков или как подпроцессы. Число параллельных скачиваний на источник задаётся в конфиге: по умолчанию 3 для Soulseek и 2 для YouTube Music.
- **Лимитеры на сервис:**
  - MusicBrainz — 1 запрос/с;
  - AcoustID — 3/с;
  - LRCLIB — 300 мс между запросами;
  - Cover Art Archive — 5/с.
- **Повторы.** Сетевые ошибки и 5xx — экспоненциальный отступ с джиттером, до 5 попыток. На 429 и 503 соблюдается `Retry-After`. Другие 4xx сразу считаются отказом.
- **Изоляция ошибок.** Ошибка одного трека никогда не останавливает очередь. Если ломается источник целиком (slskd недоступен, «стена» YouTube), на паузу встаёт только этот источник.
- **Логи.** Строки JSON пишутся в файл в каталоге данных, ротация по 10 МБ. В консоль — `rich`.

CLI (`trawl …`):

| `run [--once\|--watch]` | обработать очередь; `--watch` — по расписанию из конфига: синк вкуса, новые релизы, очередь, повтор `missing`, апгрейд |

- очередь и прогресс по источникам;
- паузы источников;
- ленту событий;
- список отказов и `unresolved`.

Для отказа можно:
- посмотреть кандидатов с оценками и причинами отказа;
- выбрать одного вручную;
- вставить свою ссылку;
- пометить `skipped`.

## Конфиг и секреты

- **`config.toml`** лежит по умолчанию в `platformdirs.user_config_dir("trawl")`. Путь можно переопределить через `--config` или `TRAWL_CONFIG`. В конфиге:
  - пути и email для User-Agent;
  - порядок и параметры источников;
  - правила выбора релиза;
  - уровни вкуса и `likes.scope`;
  - жанры;
  - лимиты и расписание.
- **`secrets.toml`** лежит рядом и в репо не попадает. В нём токены Яндекса и Spotify (client id и refresh token), ключ API и адрес slskd, ключ AcoustID, путь к cookies YouTube.
- Пример конфига хранится в репо как `config.example.toml`. Неизвестный ключ в конфиге — ошибка при старте с указанием строки.

- **CI:** `ruff check`, `ruff format --check`, `pyright`, `pytest` на Windows и Ubuntu с установленными ffmpeg, fpcalc и rsgain.

## Порядок сборки

Каждый шаг заканчивается рабочей программой и зелёным CI.

1. Каркас, конфиг и секреты, база, миграции и переходы, клиент MusicBrainz, план, `add` по ссылке MusicBrainz и тексту, `status`, `explain`, `doctor`.
2. Источник `ytmusic`, пробник, проверка, теги, обложки, тексты, ReplayGain, staging и библиотека: первый альбом от `add` до файлов.
3. Источник `soulseek`, смена издания в группе, апгрейд до без потерь.
4. Источник `local`, перепаковка в FLAC.
5. `resolve/` и вкус: ListenBrainz, Яндекс, Spotify, `unresolved` и `link`.
6. Новые релизы, `follow`, `run --watch`, запуск через планировщик Windows и systemd.
7. TUI.

## Риски

- **Неофициальные API Яндекса и YouTube Music** могут сломаться без предупреждения. Их клиенты изолированы: падает только сломанный источник.
- **Spotify Development Mode** требует Premium у владельца, а условия API меняются. Если Spotify закроет доступ, отключается только `sync-taste spotify`.
- **Небольших артистов может не быть в MusicBrainz или AcoustID.**
  - Нет в AcoustID → закрывает правило длительности.
  - Нет в MusicBrainz → trawl это не закрывает. Такие желания лежат в `unresolved`, пока релиз не добавят в MusicBrainz руками.
- **Soulseek — P2P-обмен, где принято раздавать.** Раздавать ли папку библиотеки, решает владелец в настройках slskd. trawl этого не делает.
- **YouTube и Soulseek — серая зона.** Поэтому репо приватное.
